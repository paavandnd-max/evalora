## Current verification

- `py -m unittest -v`: 47 tests passed on 2026-10-19, including explicit missing-judge account creation, display-name judge assignment, sensitive workspace-file route isolation, private/missing GitHub failures, archive resource-boundary, DNS destination, high-volume rate-limit burst, concurrent duplicate-submission, end-to-end stalled-body 408 handling, compressed-stream, secure-cookie configuration, reviewer IDOR, cross-language N/A, and parser regression cases.
- `py -m py_compile server.py test_evalora.py` and `git diff --check`: passed after the latest changes.
- `git diff --check` returned no diagnostics, but this workspace currently reports project files as untracked, so Git's tracked-diff check does not validate their whitespace.
- Restart-time schema check confirmed the existing local `problems` table migrated to include `reference_dataset_json`.
- Local app is in isolated demo mode; its fixture data is separate from Supabase. The connected Supabase project has the multi-event schema and reviewer-only RLS policies. It currently contains zero events and zero submissions after removal of the empty migration seed.
- Supabase migration history includes `evalora_multievent_reviewer_only_rls` and `remove_empty_legacy_event_seed`; the migration also adds the missing `repository_url` and `evaluation_report` columns when upgrading an existing submissions table.
- Supabase migration `evalora_shared_supabase_rate_limits` adds the hashed identity counter table and an atomic PostgreSQL RPC limited to `service_role`; four independent processes issued 20 concurrent requests and exactly five were allowed. Fixed-window reset passed, and test rows were removed.
- Supabase migrations `evalora_submission_repository_uniqueness` and `evalora_conditional_repository_duplicate_guard` add the event/team/repository lookup index and a `23505` trigger guard when resubmissions are disabled; the guard is conditional so explicitly enabled resubmissions remain supported.
- Supabase security advisors still report the intentionally exposed boolean authorization helper functions as `SECURITY DEFINER`, the service-role-only rate-limit table as RLS-without-policy, and leaked-password protection as disabled. The first two are currently deliberate implementation choices (helpers are used by RLS and the counter is service-role-only); leaked-password protection is a project-level setting that should be enabled before production authentication.
- A temporary Supabase-mode HTTP smoke server on port 8001 returned HTTP 200 for `/` and `/api/public-events`, reported zero open events, and returned 401 for unauthenticated `/api/state`; it was stopped after the read-only check.
- The main application server remains in local demo mode on port 8000 so manual testing does not write to Supabase until staff credentials and the desired storage mode are confirmed.
